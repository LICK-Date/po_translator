# PO LLM Translator 项目开发规格说明书

## 1. 项目目标

开发一个面向 `.po` / `.pot` 本地化文件的 LLM 辅助翻译工具。

软件必须能够：

1. 读取 GNU gettext `.po` / `.pot` 文件。
2. 提取需要翻译的字符串。
3. 对原文进行全局分析。
4. 自动发现候选术语。
5. 使用 LLM 对候选术语进行筛选、规范化和翻译。
6. 建立项目级术语表 Glossary。
7. 在术语表约束下批量翻译 PO 条目。
8. 自动保护格式占位符、变量、标签和转义内容。
9. 对 LLM 输出进行确定性校验。
10. 对失败条目进行重试、修复或标记人工审核。
11. 保存翻译进度，支持中断后继续。
12. 使用 Translation Memory 避免重复调用 LLM。
13. 允许用户自行配置兼容 OpenAI API 的 LLM 服务。
14. 最终安全写回新的 `.po` 文件，不破坏原有 PO 元数据。

本项目不是简单的“一行文本调用一次 LLM”的翻译程序。

核心设计原则为：

> 确定性处理由程序负责，语义判断由 LLM 负责。

例如：

- PO 解析由程序负责。
- 字符串去重由程序负责。
- 占位符提取由程序负责。
- 占位符一致性校验由程序负责。
- 缓存由程序负责。
- 术语候选统计由程序负责。
- 术语是否具有翻译价值由 LLM 判断。
- 实际自然语言翻译由 LLM 完成。
- 翻译质量审阅可由 LLM 完成。
- 最终格式是否合法必须由程序判断。

# 5. Domain Model

PO 文件不得直接作为核心业务数据结构。

必须定义程序内部领域模型。

## TranslationEntry

推荐：

```python
@dataclass
class TranslationEntry:
    id: str

    msgid: str
    msgid_plural: str | None

    msgctxt: str | None

    msgstr: str
    msgstr_plural: dict[int, str]

    comments: list[str]
    extracted_comments: list[str]
    occurrences: list[tuple[str, str]]
    flags: set[str]

    is_obsolete: bool
    is_fuzzy: bool

    status: TranslationStatus
```

`id` 必须由程序内部生成。

不得使用列表位置作为唯一 ID。

建议使用以下内容计算稳定 hash：

```text
msgctxt
+
msgid
+
msgid_plural
+
occurrence
```

---

# 6. TranslationStatus

至少定义：

```python
class TranslationStatus(Enum):
    PENDING = "pending"
    TRANSLATING = "translating"
    TRANSLATED = "translated"
    CACHED = "cached"
    FAILED = "failed"
    REVIEW_REQUIRED = "review_required"
    SKIPPED = "skipped"
```

任何翻译任务都必须具有明确状态。

禁止使用：

```python
translated = True
```

这种过于简单的状态设计。

# 7. PO 文件读取规则

必须使用经过验证的 PO 解析库，例如：

```text
polib
```

不要自己从头实现 PO parser。

读取时必须保留：

```text
msgid
msgid_plural
msgstr
msgstr_plural
msgctxt
comments
tcomment
occurrences
flags
obsolete
```

保存时不得无故删除：

```text
comments
source references
flags
context
plural forms
metadata
```

# 8. PO 翻译筛选逻辑

默认待翻译项：

```text
msgid 非空
AND
not obsolete
AND
msgstr 为空
```

对于 fuzzy：

默认策略：

```text
不自动覆盖
```

但设置中允许用户选择：

```text
跳过 fuzzy
重新翻译 fuzzy
仅人工审核 fuzzy
```

已有译文默认不得覆盖。

必须提供：

```text
Translate untranslated only
Translate all
Translate fuzzy only
```

三种模式。


## HTML/XML

```text

```

## 转义


---

# 10. Placeholder 校验原则

翻译前后：

```text
placeholder 类型
数量
名称
```

必须一致。

例如：

```text
Hello {username}
```

不能翻译为：

```text
你好 {用户名}
```

必须保持：

```text
你好 {username}
```

对于：

```text
HP: {current}/{max}
```

翻译后必须同时存在：

```text
{current}
{max}
```

顺序是否允许变化可根据 placeholder 类型配置。

# 11. 术语系统总体流程

术语处理采用：

```text
程序统计
↓
候选术语
↓
LLM筛选
↓
LLM翻译
↓
用户审核
↓
锁定 Glossary
↓
正文翻译
```

禁止直接：

```text
全文 → LLM生成术语
```

作为唯一方案。

LLM 可以补充术语，但程序必须先产生候选。

---

# 12. 候选术语提取

初始版本主要针对：

```text
中文
日文
英文
```

候选提取需要独立模块：

```text
terminology/extractor.py
```

对于中文：

默认寻找：

```text
长度 >= 2
长度 <= configurable max length
出现次数 >= 2
```

但不得简单枚举全部 substring 后直接交给用户。

必须加入：

```text
频率过滤
长度过滤
重叠过滤
字符类型过滤
stop words
```

建议候选包含：

```python
@dataclass
class TermCandidate:
    text: str
    frequency: int
    length: int
    examples: list[str]
    score: float
```

---

# 13. 候选术语去噪

以下通常不应该作为术语：

```text
常用助词
普通标点
单独数字
纯占位符
过短字符串
明显字符串残片
```

例如：

```text
装备强化成功
装备强化失败
```

候选可能有：

```text
装备
强化
装备强化
强化成功
强化失败
```

算法不能认为全部都是正式术语。

这一层只负责候选，不负责最终判断。

---

# 14. LLM 术语筛选

候选术语批量发送给 LLM。

必须要求 Structured Output。

目标格式：

```json
{
  "terms": [
    {
      "source": "装备强化",
      "keep": true,
      "category": "game_system",
      "reason": "..."
    }
  ]
}
```

程序只信任：

```text
source
keep
category
```

`reason` 仅用于 UI 展示，不参与程序决策。

如果返回 JSON 无法解析：

```text
重试一次
↓
仍失败
↓
整个 batch 标记 FAILED
```

不得偷偷从自然语言中用正则猜 JSON。

---

# 15. Glossary Model

```python
@dataclass
class GlossaryTerm:
    id: str

    source: str
    target: str | None

    category: str | None

    description: str | None

    locked: bool

    frequency: int

    created_by: str
```

`created_by` 可为：

```text
algorithm
llm
user
import
```

---

# 16. Glossary 优先级

用户手动修改后的术语：

```text
locked = True
```

锁定术语禁止被 LLM 自动重新翻译。

优先级：

```text
User locked
>
Imported
>
Reviewed LLM
>
Automatic candidate
```

# 17. 术语翻译

术语筛选完成后，统一批量翻译术语。

输入：

```json
{
  "source_language": "ja",
  "target_language": "zh-CN",
  "terms": [
    "魔導石",
    "王都",
    "聖騎士"
  ]
}
```

输出：

```json
{
  "translations": [
    {
      "source": "魔導石",
      "target": "魔导石"
    }
  ]
}
```

术语翻译完成以后，用户可以修改。

用户确认后才能进入正文正式翻译。

但设置允许：

```text
Auto approve glossary
```

默认关闭。

---

# 18. 术语匹配

正式翻译每个 batch 时：

禁止发送整个 Glossary。

必须先检测 batch 中实际出现的术语。

例如 Glossary 有：

```text
2000
```

条术语。

当前 batch 只包含：

```text
16
```

条。

则 prompt 中只能加入这 16 条相关术语。

接口：

```python
match_glossary(
    text: str,
    glossary: list[GlossaryTerm]
) -> list[GlossaryTerm]
```

初版可使用：

```text
Trie
Aho-Corasick
或可靠 substring matcher
```

如果实现复杂度过高，第一版本可采用优化后的字符串匹配，但必须与 UI 解耦。

---

# 19. Translation Memory

必须实现 Translation Memory。

目的：

避免完全相同文本重复调用 LLM。

TM Key 至少包含：

```text
source_language
target_language
msgid
msgctxt
```

另外必须考虑：

```text
glossary version
prompt version
```

推荐 hash：

```python
sha256(
    source_language
    + target_language
    + msgctxt
    + msgid
    + glossary_hash
    + translation_profile
)
```

---

# 20. Translation Memory 命中

翻译流程：

```text
Entry
↓
TM lookup
├─ HIT → CACHED
└─ MISS → LLM
```

TM 命中不得调用 LLM。

用户可以：

```text
Disable translation memory
Clear project TM
```

# 26. Batch Translation

严禁：

```text
一个 Entry = 一个 API 请求
```

默认采用 batch。

例如：

```text
20~50 entries / batch
```

但不能只以数量切 batch。

同时限制：

```text
总字符长度
估算 token
```

推荐配置：

```text
max_entries_per_batch = 30
max_chars_per_batch = 10000
```

---

# 27. Batch 请求协议

每个 Entry 使用内部 ID。

请求：

```json
{
  "entries": [
    {
      "id": "abc123",
      "text": "Start Game"
    },
    {
      "id": "abc124",
      "text": "Load Game"
    }
  ]
}
```

LLM：

```json
{
  "translations": [
    {
      "id": "abc123",
      "translation": "开始游戏"
    },
    {
      "id": "abc124",
      "translation": "读取游戏"
    }
  ]
}
```

禁止要求 LLM 返回原文作为映射依据。

必须使用 ID。

```text
内容类型
翻译要求

占位符保护规则
```

# 29. 翻译 Pipeline

Pipeline 必须可配置。

默认：

```text
TM Lookup
↓
Initial Translation
↓
Placeholder Validation
↓
Glossary Validation
↓
Structural Validation
↓
Accept / Repair / Retry
```

不得默认所有文本使用三阶段 Reflection。

---

# 30. 翻译模式

至少支持：

## Fast

```text
Translate
↓
Validate
```

## Quality

```text
Translate
↓
Reflection
↓
Improve
↓
Validate
```

## Smart

推荐默认：

```text
Translate
↓
Validate
↓
if suspicious:
    Reflection
    Improve
↓
Validate
```

Smart 模式应作为长期推荐模式。

---

# 31. Reflection

Reflection 输入：

```text
Source
Initial Translation
Relevant Glossary
Context
```

输出：

```json
{
  "issues": [
    {
      "type": "terminology",
      "description": "..."
    }
  ],
  "needs_revision": true
}
```

如果：

```text
needs_revision = false
```

无需调用 Improve。

---

# 32. Improve

只有 Reflection 判断需要修改时调用。

输出：

```json
{
  "translation": "..."
}
```

之后必须再次执行全部 deterministic validators。

# 33. Validator

必须独立于 LLM。

至少包含：

```text
PlaceholderValidator
EmptyTranslationValidator
GlossaryValidator
StructureValidator
EntryCountValidator
JSONValidator
```

统一接口：

```python
class Validator(Protocol):

    def validate(
        self,
        source,
        translation,
        context
    ) -> ValidationResult:
        ...
```

---

# 34. ValidationResult

```python
class ValidationResult:

    valid: bool

    errors: list[ValidationIssue]

    warnings: list[ValidationIssue]
```

错误与警告必须区分。

例如：

```text
placeholder 丢失 = ERROR
术语疑似不一致 = WARNING / ERROR
译文过长 = WARNING
```

---

# 35. Repair

如果 placeholder 错误：

优先使用专门 Repair Prompt。

例如：

```text
The following translation has incorrect placeholders.

Source:
Hello {username}

Incorrect translation:
你好 {用户名}

Required placeholders:
{username}

Fix only the translation.
Do not change its meaning.
```

修复后再次 validator。

---

# 36. Retry 策略

错误分类：

## 网络

```text
timeout
connection reset
HTTP 429
HTTP 5xx
```

允许自动 retry。

## 内容

```text
invalid JSON
missing ID
placeholder broken
```

允许有限次数 repair / retry。

## 配置

```text
401
403
invalid model
invalid URL
```

立即停止任务。

禁止无限 retry。

---

# 37. Retry Backoff

网络错误：

```text
exponential backoff
```

例如：

```text
1s
2s
4s
8s
```

增加随机 jitter。

默认最大：

```text
3~5 retries
```

---

# 38. Rate Limiter

必须独立模块实现。

同时支持：

```text
RPM
max concurrency
```

例如：

```text
max_concurrency = 5
rpm = 60
```

即使同时创建 5 个 worker，也必须遵守 RPM。

```text
Semaphore
```


# 79. Codex 实现要求

Codex 在开发过程中必须遵守：

1. 不擅自改变整体架构。
2. 不因为方便而把业务逻辑写进 GUI。
3. 不因为方便而让 PO parser 调用 LLM。
4. 不因为方便而让 LLM client 操作数据库。
5. 每完成一个 Phase，首先运行测试。
6. 测试失败不得继续堆后续功能。
7. 不删除测试来使 CI 通过。
8. 不用大量 mock 代替核心逻辑测试。
9. 所有网络接口均需要 timeout。
10. 所有循环 retry 都必须存在最大次数。
11. 所有后台任务都必须可结束。
12. 数据写入不得依赖应用正常退出。
13. 用户数据安全优先于翻译完成率。
14. 如果翻译结果无法通过 validator，应标记失败，而不是强行写入。

# 81. 优先级原则

发生冲突时按以下优先级：

```text
PO 数据安全
>
翻译正确性
>
可恢复性
>
API 成本
>
性能
>
UI 美观
```

换言之：

宁可：

```text

```

也不能写入可能损坏文件或破坏变量的翻译。

宁可：

```text
让用户人工审核
```

也不能因为 LLM 看起来“差不多正确”就绕过 validator。

# 82. 最终产品设计原则

整个系统应遵循：

```text
Parser
负责理解文件结构

Term Engine
负责发现候选术语

LLM
负责语义判断与语言生成

Glossary
负责全局一致性

Translation Memory
负责避免重复工作

Validator
负责防止 LLM 破坏格式

Storage
负责保证任务可恢复

UI
负责让用户控制整个流程
```

最终系统应是：

> 一个具有 LLM 翻译能力的本地化工程工具。

而不是：

> 一个能够上传 PO 文件的聊天机器人。

任何架构决策都应围绕这一目标进行。
